## OAuth2 — jak działa w n8n 2.43.4 (sprawdzone w kodzie źródłowym)

Źródła: `packages/cli/src/oauth/oauth.service.ts`,
`controllers/oauth/oauth2-credential.controller.ts`,
`@n8n/backend-services/src/services/url.service.ts`, `@n8n/config` (tag `n8n@2.43.4`).

1. **Redirect URI** = `getInstanceBaseUrl()` + `/rest/oauth2-credential/callback`, gdzie
   `getInstanceBaseUrl()` = `N8N_EDITOR_BASE_URL` (a gdy pusty — URL webhooków).
   n8n pokazuje go w credentialu jako „OAuth Redirect URL”.
2. **Brak osobnej zmiennej dla callbacku.** Host callbacku zawsze jest hostem edytora.
3. **Callback wymaga sesji n8n.** Trasa ma `allowUnauthenticated: true`, ale serwis
   sprawdza `req.user` (ciasteczko `n8n-auth`, przypisane do hosta) i `userId` ze `state`;
   wyjątek tylko przy `N8N_SKIP_AUTH_ON_OAUTH_CALLBACK=true` (domyślnie `false` od 2.0).
   `state` zawiera jednorazowy token CSRF z pamięcią po stronie serwera (TTL, ochrona przed powtórzeniem).
   `N8N_OAUTH_BROWSER_BINDING=true` dodaje ciasteczko `n8n-oauth-binding` (ścieżka `/rest`),
   więc flow musi wrócić do tej samej przeglądarki.
4. **Callback to przekierowanie przeglądarki**, a nie połączenie od dostawcy. Dostawca
   (Google, Microsoft, GitHub) nigdy nie łączy się z adresem callbacku. Wymiana kodu na
   token to połączenie wychodzące n8n → dostawca.

**Wybrane rozwiązanie:** edytor = host callbacku = `https://n8n.tdcode.pl/`, publicznie
przez istniejący Cloudflare Tunnel, chroniony standardowym logowaniem n8n
(`N8N_SECURE_COOKIE=true`, `N8N_SKIP_AUTH_ON_OAUTH_CALLBACK=false`,
`N8N_OAUTH_BROWSER_BINDING=true`). Domena publiczna, więc przyjmie ją Google.
Zmiana adresu wymaga tylko `n8n_editor_url` w `host_vars/n8n01.yml`.

`N8N_WEBHOOK_URL` (następca przestarzałego `WEBHOOK_URL`) ustawia bazę URL webhooków
produkcyjnych **i testowych**. Adres testowy w edytorze (`https://webhookn8n.tdcode.pl/webhook-test/...`)
jest publicznie zablokowany; testuj przez host edytora: `https://n8n.tdcode.pl/webhook-test/<ścieżka>`.

### 4. Publiczne webhooki (Cloudflare Tunnel) — ręcznie

Konfiguracja tunelu jest poza repozytorium (rola `cloudflared` tylko instaluje pakiet).
W tunelu `path` to wyrażenie regularne **bez domyślnego zakotwiczenia**. Reguły są
sprawdzane od góry, pierwsza pasująca wygrywa, a ostatnia musi być catch-all.
Dlatego `^` na początku i osobna reguła 404 dla hosta.

- tunel lokalny (`/etc/cloudflared/config.yml` na `cloudflare01`): kopia pliku, potem
  dodaj **przed** końcową regułą `- service: http_status:404`:

  ```yaml
    - hostname: webhookn8n.tdcode.pl
      path: ^/webhook/
      service: http://192.168.55.31:5678
    - hostname: webhookn8n.tdcode.pl
      service: http_status:404
  ```

  ```bash
  sudo cloudflared tunnel ingress validate
  sudo cloudflared tunnel ingress rule https://webhookn8n.tdcode.pl/webhook/ping            # reguła n8n
  sudo cloudflared tunnel ingress rule https://webhookn8n.tdcode.pl/rest/login              # 404
  sudo cloudflared tunnel ingress rule https://webhookn8n.tdcode.pl/x/webhook/              # 404
  sudo cloudflared tunnel ingress rule https://webhookn8n.tdcode.pl/rest/oauth2-credential/callback  # 404
  cloudflared tunnel route dns <tunel> webhookn8n.tdcode.pl
  sudo systemctl restart cloudflared
  ```

- tunel zarządzany z panelu (Zero Trust → Networks → Tunnels → Public Hostname):
  subdomena `webhookn8n`, domena `tdcode.pl`, **Path** `^/webhook/`, Service `HTTP`,
  URL `192.168.55.31:5678`. Żadnego wpisu `webhookn8n` bez ścieżki — reszta trafia
  do domyślnej reguły 404.

Tunel to nie jedyna granica. Dodatkowo:
- **Cloudflare WAF** → Custom rule *Block*:
  `(http.host eq "webhookn8n.tdcode.pl" and not starts_with(http.request.uri.path, "/webhook/"))`.
- **Normalizacja URL** (Rules → Settings → Normalize incoming URLs) włączona, żeby
  `/webhook/../rest/...` nie omijało reguł ścieżek.
- Edytor i API nadal wymagają logowania n8n, a callback OAuth2 wymaga sesji.

Na `webhookn8n.tdcode.pl` **nie** włączaj Cloudflare Access, Bot Fight Mode ani wyzwań
(challenge). Blokują one żądania weryfikacyjne dostawców (np. `GET` z `hub.challenge`,
Slack `url_verification`). Uwierzytelnianie i podpisy konfiguruj per workflow
(Header Auth w węźle Webhook lub weryfikacja podpisu dostawcy).

## Konfiguracja OAuth2 u dostawców

Redirect URI dla **wszystkich** dostawców OAuth2 (sprawdź, że jest identyczny z polem
„OAuth Redirect URL” w credentialu n8n):

```text
https://n8n.tdcode.pl/rest/oauth2-credential/callback
```

Credential łącz zawsze z przeglądarki zalogowanej do `https://n8n.tdcode.pl`.
Przycisk „Connect/Sign in” otwiera okno dostawcy, które wraca na callback.

### Przykład: Google (Gmail, Calendar, Drive, Sheets)

1. Google Cloud Console → nowy projekt → *APIs & Services → Library*: włącz Gmail API,
   Google Calendar API, Google Drive API, Google Sheets API (tylko potrzebne).
2. *Google Auth Platform → Branding/Audience*: typ **External** (lub Internal dla
   Workspace), authorized domain `tdcode.pl`, w trybie Testing dodaj swoje konto do *Test users*.
3. *Clients → Create client → Web application* → **Authorized redirect URIs**:
   `https://n8n.tdcode.pl/rest/oauth2-credential/callback`
   (JavaScript origins niepotrzebne).
4. n8n → Credentials → np. *Gmail OAuth2 API* lub *Google OAuth2 API* z zakresami →
   wklej Client ID i Client Secret → *Sign in with Google*.

Ograniczenia Google:
- redirect URI musi mieć publiczną domenę najwyższego poziomu i HTTPS;
- w trybie *Testing* (External) refresh tokeny wygasają po 7 dniach, więc credential
  trzeba łączyć ponownie. Tryb *In production* bez weryfikacji pokazuje ostrzeżenie
  „unverified app” i ma limit użytkowników. Zakresy Gmail/Drive są wrażliwe/ograniczone;
- jeden OAuth client może obsłużyć wiele credentiali n8n (Gmail, Calendar, Drive, Sheets).

### Przykład: dostawca generyczny (OAuth2 API)

1. U dostawcy zarejestruj aplikację typu *web/confidential*, redirect URI jak wyżej.
2. n8n → Credentials → **OAuth2 API**: Grant Type *Authorization Code* (lub *PKCE*,
   jeśli dostawca wspiera), *Authorization URL*, *Access Token URL*, *Client ID*,
   *Client Secret*, *Scope* (np. z `offline_access`, jeśli dostawca wymaga go dla
   refresh tokenu), *Authentication*: Header (Basic) lub Body, zgodnie z dokumentacją
   dostawcy → *Connect my account*.

### Microsoft i GitHub — skrót

- **Microsoft Entra ID**: App registrations → New → platforma **Web**, redirect URI
  jak wyżej; Certificates & secrets → client secret (ma datę ważności, maks. 24
  miesiące, więc trzeba zaplanować odnowienie). W n8n credential *Microsoft ... OAuth2 API*.
- **GitHub**: Settings → Developer settings → OAuth Apps → *Authorization callback URL*
  jak wyżej (jedna aplikacja = jeden callback). W n8n credential *GitHub OAuth2 API*.

Google, Microsoft i GitHub nie łączą się z redirect URI (to przekierowanie przeglądarki).
Nie otwieraj `/rest` na `webhookn8n.tdcode.pl`.

Nie zautomatyzowane — do zaplanowania razem z resztą backupu (`docs/backup/`).

  ```bash
  ssh tom@192.168.55.31 'cd /opt/n8n && sudo docker compose exec -T postgres \
    pg_dump -U n8n -d n8n -Fc' > n8n-$(date +%F).dump
  ```

  (lub na VM do `/opt/n8n/backups/`, potem poza VM, np. QNAP przez `iza`).

  pustej bazy → restart `n8n`. Z innym kluczem poświadczenia są nie do odszyfrowania.
- Zmiana `n8n_editor_url` po podłączeniu credentiali zmienia redirect URI. Trzeba wtedy
  zaktualizować go u każdego dostawcy, ale już zapisane tokeny działają dalej.
